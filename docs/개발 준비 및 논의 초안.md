# 개발 준비 및 논의 초안

작성일: 2026-11-05  
상태: 팀 검토용 초안

구현을 시작하기 전에 팀이 합의할 내용과 역할별 준비 작업, 개발 순서를 정리합니다.
기존 프로젝트 계획서 v1.3, SRS v0.2, SDD v0.1과 현재 역할 배분을 기준으로 작성했습니다.
아래 제안은 확정 사항이 아니며 팀 논의 후 결정 기록에 반영합니다.

## 현재 정해진 방향

- 부산 공공시설의 예상요금·감면·예약·취소·환불 조건을 비교합니다.
- AI는 자연어에서 검색 조건을 추출하고 사용자가 확인·수정합니다.
- 최종 요금 계산과 감면 적용은 백엔드 규칙 엔진이 담당합니다.
- 근거가 없거나 규정이 충돌하면 임의 계산하지 않고 ‘확인 필요’로 표시합니다.
- 직접 예약·결제, 실시간 잔여석 확인, 관리자 웹 UI는 구현 범위에서 제외합니다.
- 규정상 이용조건 충족 여부와 실제 예약 가능 여부를 구분합니다.
- 작업은 Issue → 기능 브랜치 → PR → 다른 팀원 리뷰 → develop 병합으로 진행합니다.

## 먼저 함께 결정할 내용

| 논의 항목 | 제안 초안 | 결정할 내용 |
|---|---|---|
| 대상 시설 | 동일 유형의 비교 가능한 시설 3~5곳 조사 | 시설 유형과 최종 목록 |
| 프론트엔드 | SDD의 React·TypeScript·Vite 제안 검토 | 담당자 경험과 구현 가능 여부 |
| 백엔드 | SDD의 Python FastAPI 제안 검토 | 담당자 경험과 구현 가능 여부 |
| DB | SQLite와 PostgreSQL 비교 | 공동 개발·배포에 맞는 방식 |
| AI | 구조화된 조건 추출을 지원하는 API 사용 | 제공자·모델·비용 한도 |
| 일정 | 작은 통합 기능부터 완성 | 최종 발표일과 중간 점검일 |

기술 스택을 선택할 때 버전과 패키지 관리 도구도 함께 정합니다.
시설은 공식 자료 확보 여부를 기준으로 선정합니다.
기본요금뿐 아니라 추가요금·감면·예약·환불 조건, 출처 URL·확인일·데이터 이용조건을 확인해야 합니다.
문서의 시설 예시와 요금 예시를 실제 검증 데이터로 사용하지 않습니다.

## 개발 전에 구체화할 설계

SDD에 화면 흐름과 API 초안이 있으므로 이를 바탕으로 세부 형식을 합의합니다.

| 영역 | 합의할 내용 |
|---|---|
| 화면 | 필수 입력값, 후보 선택 방식, 비교표 항목, 오류와 ‘확인 필요’ 표시 |
| 검색 조건 | 종목·지역·날짜·시간·인원·감면 유형의 필수 여부와 형식 |
| 시설·규정 데이터 | 요금 단위, 추가요금, 감면 중복 여부, 적용 기간, 출처·확인일 |
| 계산 결과 | 최초 납부액·예상 환급액·환급 후 예상 부담액 구분 |
| 예외 처리 | 입력 오류, 검색 결과 없음, 규정 누락·충돌, AI 실패 응답 |
| 공통 API | 요청·응답 JSON 예시, 오류 형식, API별 담당과 변경 공유 방법 |

직접 입력과 AI 추출은 같은 검색 조건 형식을 사용합니다.
AI 실패 시 직접 입력으로 진행할 수 있도록 하고, API 키와 개인정보가 응답·로그에 노출되지 않도록 설계합니다.
‘확인 필요’ 항목이 있으면 불완전한 합계를 확정 금액처럼 표시하지 않습니다.
모든 세부사항을 한 번에 확정하기보다 첫 통합 기능 구현에 필요한 계약부터 맞춥니다.

## 역할별 첫 작업 제안

| 담당 | 첫 작업 | 완료 기준 |
|---|---|---|
| 김규성 | 논의 취합, AI 입력·출력 초안, 개발 환경·CI 계획 | 미확정 항목과 AI 연동 경계 정리 |
| 왕연호 | 시설 후보·공식 규정 조사, 데이터 구조 초안 | 출처·확인일과 실제 계산 사례 확보 |
| 김승일 | 입력 → 후보 → 비교 화면 초안, 프론트 스택 검토 | 화면별 입력·출력 항목 정리 |
| 배승환 | 백엔드 스택 검토, API·규칙 엔진 입출력 보완 | 요청·응답 예시와 계산 처리 순서 정리 |

각자 초안을 만든 뒤 함께 검토하고, 확정된 작업부터 담당자·완료 기준·기한을 정해 Issue로 등록합니다.
공통 API나 데이터 구조처럼 다른 영역에 영향을 주는 사항은 구현 전에 공유합니다.
SDD의 AI 컴포넌트 담당 제안은 현재 역할 배분과 맞춰 후속 갱신합니다.

## 개발 순서 제안

| 단계 | 작업 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| 1 | 시설 조사와 기술 스택 합의 | 시설 선정 근거와 스택·버전 결정 기록 |
| 2 | 검색 조건·데이터·API 형식 합의 | 첫 기능의 요청·응답·규정 데이터 예시 합의 |
| 3 | 프로젝트 기본 구조와 실행 환경 구성 | 팀원 모두 같은 절차로 실행, 기본 검사 수행 |
| 4 | 시설 1곳으로 직접 입력 → 계산 결과 표시 | 공식 계산 사례와 결과 일치, 출처 표시 |
| 5 | 시설 확장과 검색·비교·체크리스트 구현 | 시설 2곳 이상 비교, 규정 누락·예외 표시 |
| 6 | AI 조건 추출 연동 | 사용자 확인·수정과 실패 시 직접 입력 동작 |
| 7 | 통합 테스트·배포·시연 준비 | 선정 시설 데이터 검증과 SRS 인수 기준 점검 |

시설 1곳 구현은 중간 통합 목표입니다.
최종 목표는 기존 계획에 따라 공식 근거가 확인된 동일 유형 시설 3곳 이상을 확보하고 핵심 기능을 검증하는 것입니다.
AI 담당자는 핵심 기능 개발과 병행해 추출 실험을 진행할 수 있으며, 공통 입력 형식 합의 후 서비스에 연결합니다.

## 첫 통합 목표와 검증

첫 목표는 공식 규정이 확인된 시설 1곳에 대해 직접 입력한 조건으로 예상요금과 근거를 표시하는 것입니다.
기본요금·추가요금·감면·선결제 후 환급·규정 누락 사례를 실제 시설 규정에 맞춰 준비합니다.
예상 결과와 규칙 엔진 결과가 일치하는지 확인한 뒤 시설 비교로 확장합니다.

AI 조건 추출 정확도 목표·평가 질의 수와 성능 측정 환경·표본 수는 별도 합의합니다.
비교 응답 시간 등 기존 SRS의 인수 기준을 시험 계획에 연결합니다.

## 팀원 검토 요청

- 각자 담당 영역의 스택 의견과 구현 가능 여부를 공유합니다.
- 시설 후보와 공식 규정 확보 가능 여부를 확인합니다.
- 역할별 첫 작업의 범위와 예상 소요 시간을 검토합니다.
- 최종 발표일과 각자 가능한 시간을 확인해 중간 일정을 정합니다.
- 합의한 사항은 [결정 기록](decisions.md)에 결정일·이유·관련 Issue 또는 PR과 함께 남깁니다.
- 범위나 설계가 바뀌면 관련 SRS·SDD·테스트 기준도 함께 갱신합니다.
