# 공통 실행 및 검사 안내

실제 시설 데이터로 실행하는 절차입니다. 저장소 루트에서 시작하며, 백엔드와 프론트는 서로 다른 터미널에서 실행합니다.

## 준비

- Python 3.13: GitHub Actions 검사 기준입니다.
- Node.js 24와 npm: Node 설치 후 `node --version`, `npm --version`으로 확인합니다.
- 백엔드는 `backend/requirements.txt`, 프론트는 `frontend/package-lock.json`을 기준으로 설치합니다.
- Gemini 키는 자연어 입력을 실험할 때만 필요합니다. 직접 입력·시설 검색·요금 비교·자동 검사는 키 없이 동작합니다.

```powershell
git clone https://github.com/GGS126/busan-public-facility.git
cd busan-public-facility
git switch develop
```

이미 작업 중인 저장소라면 미커밋 변경을 확인하고 최신 코드를 받습니다. 다른 사람의 개발 파일을 덮어쓰지 않습니다.

## 1. 백엔드 준비 — Windows PowerShell

프로젝트 루트에서 한 번 실행합니다. 가상환경 활성화는 필요하지 않습니다.

```powershell
python -m venv .venv
./.venv/Scripts/python -m pip install -r backend/requirements.txt
./.venv/Scripts/python database/build_db.py
Copy-Item backend/.env.example backend/.env
```

`backend/.env`가 이미 있으면 복사 단계를 생략해 기존 설정을 유지합니다. 자연어 입력을 사용할 때만 편집기로 `GEMINI_API_KEY`를 입력합니다. 키를 채팅·Issue·커밋에 올리지 않습니다.

다음 명령으로 서버를 실행하고 터미널을 열어 둡니다.

```powershell
cd backend
../.venv/Scripts/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --env-file .env
```

- API 문서: <http://127.0.0.1:8000/docs>
- 선택지 확인: <http://127.0.0.1:8000/api/options>
- `RULE_DATA_SOURCE=sqlite`가 실제 데이터 모드입니다. DB가 없으면 서버 시작이 실패하므로 먼저 생성합니다.
- 기존 터미널에 `RULE_DATA_SOURCE=sample` 또는 잘못된 `GEMINI_MODEL`이 설정돼 있으면 `.env`보다 우선할 수 있습니다. 새 터미널에서 시작하거나 해당 환경변수만 지운 뒤 실행합니다.
- JSON 수정이나 #32 같은 데이터 변경을 받은 뒤에는 **서버를 종료(Ctrl+C) → 루트에서 DB 재생성 → 서버 재시작**합니다. 열린 SQLite 뷰어도 닫아 주세요.

## 2. 프론트 준비 — 새 터미널

프로젝트 루트에서 실행합니다.

```powershell
cd frontend
npm ci
npm run dev -- --host 127.0.0.1
```

터미널에 출력된 주소(기본 <http://127.0.0.1:5173>)를 엽니다. 개발 서버는 `/api`를 백엔드의 8000번 포트로 전달합니다.

- 기본은 실제 API입니다. `frontend/.env.local`은 별도 설정이 필요할 때만 `.env.example`을 복사해 만듭니다.
- 백엔드 없이 화면만 볼 때는 `VITE_USE_MOCK_API=true`로 설정합니다. 모의 결과를 실제 요금 검증에 사용하지 않습니다.
- 설정을 바꾸면 Vite를 다시 시작합니다. `VITE_` 값은 브라우저에 노출되므로 API 키를 넣지 않습니다.
- `npm run build`는 정적 파일 생성 검사이며, `npm run preview`로 빌드 결과를 로컬 확인할 수 있습니다. 현재 preview도 Vite의 `/api` 프록시를 이어받으므로 백엔드를 함께 실행합니다. 실제 호스팅에서는 Vite 설정이 자동 적용되지 않으므로 배포용 프록시·HTTPS를 별도로 구성합니다.

## macOS·Linux

백엔드 가상환경의 실행 파일만 `.venv/bin/python`으로 바꿉니다.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.txt
.venv/bin/python database/build_db.py
cp backend/.env.example backend/.env  # 처음 한 번만, 기존 파일은 유지
cd backend
../.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --env-file .env
```

프론트 명령은 Windows와 같습니다.

## 3. 변경 전후 검사

백엔드는 프로젝트 루트에서 다음 한 명령으로 CI와 같은 검사를 실행합니다.

```powershell
./.venv/Scripts/python scripts/check_backend.py
```

DB 재생성 → DB 감사 검증 → 백엔드 pytest 순서로 실행하고, `database/test_*.py`가 있으면 그 테스트도 실행합니다. 하나라도 실패하면 오류 코드와 함께 중단합니다. 기존 테스트가 제외되는 경우 해당 사유를 확인하며, 통과 개수를 문서에 고정하지 않습니다.

자동 검사에서는 실제 Gemini 키를 전달하지 않고 가짜 추출기를 사용합니다. 따라서 **API 키 유효성·실제 모델 응답·AI 정확도는 별도 실호출 평가 대상**입니다. 테스트용 `sample` 설정은 검사 자식 프로세스에만 적용되며 실행 중인 서비스 설정은 바꾸지 않습니다.

프론트는 `frontend`에서 실행합니다.

```powershell
npm test
npm run lint
npm run build
```

## 4. GitHub Actions

`develop`·`main` 대상 PR의 생성/갱신, 두 브랜치에 push, 수동 실행에서 `CI`가 동작합니다.

| 검사 | 실행 환경 | 내용 |
|---|---|---|
| Backend | Ubuntu / Windows, Python 3.13 | 의존성 설치, `scripts/check_backend.py` |
| Frontend | Ubuntu, Node 24 | `npm ci`, 테스트·린트·빌드 |

PR의 Checks 또는 저장소 Actions에서 결과와 실패 로그를 확인합니다. 실행에는 API 키·저장소 Secret이 필요하지 않습니다. 새 커밋이 올라오면 같은 PR의 이전 실행은 취소됩니다.

워크플로 추가만으로 브랜치 보호의 필수 검사가 자동 설정되지는 않습니다. 첫 실행 결과를 확인한 뒤 팀이 필요한 검사를 필수 조건으로 지정할 수 있습니다.

## 오류가 나면

| 증상 | 확인 |
|---|---|
| `npm` 명령을 찾지 못함 | Node.js와 npm 설치 후 새 터미널에서 버전 확인 |
| Python 모듈 없음 | `.venv`의 Python으로 설치·실행했는지 확인 |
| DB 없음 / 생성 중 파일 잠김 | 루트에서 DB 생성, 백엔드·SQLite 뷰어 종료 후 재시도 |
| 프론트에서 API 연결 실패 | 백엔드 8000번 포트 실행, Vite의 실제 출력 주소·환경변수 확인 |
| 자연어만 실패 | 키·모델·무료 호출 한도를 확인하고 직접 입력으로 계속 진행 |
| 다른 시설·이전 규정이 표시됨 | `sample`/모의 모드 여부 확인, 최신 JSON으로 DB 재생성 후 서버 재시작 |

Windows에서도 DB 검증이 UTF-8로 실행되도록 공통 검사 명령이 환경을 설정합니다. 실패 검사를 임의로 건너뛰거나 테스트 결과를 자동 성공으로 바꾸지 않습니다.
